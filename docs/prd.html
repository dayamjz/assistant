Product requirements

Run many coding agents at once, and let none of them ship unvalidated work.

Assistant is a local tool that does two things you currently do by hand. It runs a fleet of coding agents in parallel, each in its own isolated copy of a repository, and it puts a validation gate in front of your remote so no change reaches a shared branch until it has been independently reviewed, tested, documented, and linted.

How to read this document

Section 1

What Assistant is

You can run one coding agent without much trouble. The moment you want three tasks running at once you become a tab manager: you babysit sessions, copy context between repositories, and lose track of which terminal held the failing test. At the same time, the faster those agents produce changes, the less of each change you actually read before it reaches a branch other people pull from.

Assistant addresses both problems with one system. You talk to a single coordinator. It dispatches workers into isolated copies of your repositories, supervises them, and brings you only the decisions that genuinely need you. Every change a worker produces reaches a shared branch through the same gate, so "this was validated" means the same thing for every change, in every repository, whether an agent or you wrote it.

Promise 1: parallel work you can watch

Every worker runs in a real terminal you can attach to, read, and type into. Nothing happens in a hidden process. If you intervene directly in a worker's terminal, that intervention is authoritative and the coordinator reconciles around it.

Promise 2: nothing unvalidated is shared

The gate is a named remote you push to on purpose. Pushing to it is how you consent to having that change validated, fixed, pushed, and turned into a pull request. Nothing else implies that consent, and your ordinary git push keeps working as it always did.

Who this is for

One developer who operates several coding agents and whose own credentials and accountability are on the line. Everything runs on your machine, under your identity, at your initiative. Assistant is not a shared service and does not hold a team's policy.

What it is not

  • It is not continuous integration. Your CI stays the shared outer check.
  • It is not a code host, and it does not own merge policy. Your forge does.
  • It is not a model or an agent harness. It drives whichever coding agent you already use.
  • It is not a team governance platform, and it publishes facts rather than verdicts.

Section 2

Vocabulary

Every term below means exactly one thing throughout this document and in the product. Where a word appears in both the interface and the implementation, it means the same thing in both.

The interface vocabulary is narrower than this one

The terms above are the implementation vocabulary. What Assistant says to you is deliberately smaller: outcomes, consequences, and decisions. Section 6 specifies that boundary, because leaking internal mechanics into your chat is the most common way a tool like this becomes exhausting to use.

Section 3

Why the two halves merge

Orchestration and validation are usually built as separate tools. Keeping them separate costs you two state stores, two supervision loops, and two vocabularies for the same escalation. The merge makes the gate the spine: a worker's only route to a shared branch runs through it.

One state store

A task's validation state and its supervision state are the same record. Today they live in two systems that have to be reconciled by reading logs.

One escalation path

A finding that needs your judgment and a worker that is stuck arrive the same way, in the same words, with the same options.

One supervision loop

The watcher that notices a stalled worker is the watcher that notices a run held at a decision. Neither can be running while the other is not.

Section 4

Principles

These are the acceptance criteria, not aspirations. Each one names the failure it prevents, because each corresponds to a real failure in the systems this design draws from. A feature that violates one of these is wrong even if it works.

P1 The push is the consent boundary

Pushing to the gate by name authorizes that run to validate the change, apply reviewable fixes, push the branch, and open a pull request. Nothing else implies that consent.

Prevents: a tool that silently rewires origin and starts doing things with your credentials that you did not ask for. Your ordinary git push must keep behaving exactly as it always has.

P2 A pass means the same thing everywhere

The stage order is fixed and not configurable. A repository can make a stage stricter; it can never remove, reorder, or weaken one. You may skip stages for a single run, on purpose. Standing configuration may never skip a stage on your behalf.

Prevents: "it passed the gate" quietly meaning something different in each repository, which makes the claim worthless.

P3 A finding that is not classified stops for you

Every finding carries an action. If the action is missing, malformed, or unrecognized, treat it as ask. An unclassified finding is never eligible for automatic fixing.

Prevents: an agent that omits a field getting its output silently auto-applied. The safe default when you do not know whose call it is has to be yours.

P4 The reviewer never certifies its own prescription

Reviewing and fixing are separate roles with separate memory. Every review runs in a fresh context. Only the fixer keeps a session across rounds. Context crosses between rounds only as an explicit, sanitized summary of what was found and what was changed.

Prevents: a re-review that resumes the session which prescribed the fix. That seats the prescriber as the certifier, and it has shipped incorrect code accompanied by a test that blessed it and a review that found nothing.

P5 Fixes the gate writes are reviewed like code you wrote

A change the pipeline authored is author code. It gets the same adversarial review as anything else. Previous findings, fix summaries, and tests written in the same round are claims, not evidence.

Prevents: the gate trusting itself. Automatic fixes are the least-reviewed code in the system precisely because they look like housekeeping.

P6 Never lose work

Not your commits, not commits that appeared on the remote out of band, not fixes the pipeline itself created. Every history-rewriting update is anchored to a commit the run actually observed, never to the tip read a moment before pushing. When a safety fact cannot be verified against fresh state, refuse the operation and report it.

Work the pipeline holds always has a path back into your hands, including after a crash, a cancellation, or a failed run.

Prevents: the single unrecoverable failure. A refused push is an annoyance; a lost commit is not repairable. Note the specific trap: anchoring a lease to the tip you just read always succeeds and therefore protects nothing.

P7 The branch under validation does not choose what runs

Configuration that executes code or selects which agent process starts is read from your default branch at a commit resolved by a fresh fetch, never from the pushed commit. If that trusted copy cannot be read and parsed, the run stops before launching anything.

The pushed branch is untrusted input. Nothing on it may direct what executes with your credentials, and no instruction file on it may give a validation agent an identity or authority it should not have.

Prevents: a contributor landing a hostile command on a branch and having your machine run it. Also prevents a repository whose own instructions describe an agent operator from convincing the validating agent that it is that operator.

P8 An event log is not current state

A worker appends events. Current state is a separate, authoritative record with one owner that resolves it deterministically. Reading the last line of an event log is always wrong: it cannot distinguish a stale note from a live condition, and it cannot see that a run has moved past what the note describes.

Prevents: a coordinator that acts on a decision the worker already resolved, or that reports a task as blocked when its validation run finished twenty minutes ago.

P9 Supervision costs nothing until something is actionable

A cheap non-model watcher classifies every wake. It absorbs a wake only on positive evidence that work is genuinely proceeding: an active validation stage attributed to that task's branch, or a live process signal from its terminal. Absence of evidence surfaces; it never absorbs.

Prevents: two opposite failures. Waking a model on every heartbeat makes a fleet unaffordable. Absorbing wakes on a timer makes a finished or crashed worker invisible.

P10 No turn ends blind while work is under way

Whenever a task is in flight, exactly one live supervision cycle exists. If the coordinator is about to stop while work is running and no healthy watcher holds this home's lock, it is either blocked from stopping or forced into one more turn.

Prevents: the most expensive silent failure in the whole system. Work holds at a decision, nothing is watching, and you find out hours later. This warrants more than one mechanism.

P11 Isolation is asserted, never assumed

A worker does not launch unless the resolved path is a real isolated copy, distinct from the primary checkout. The check runs at launch and again in the worker's own instructions before it creates a branch. Being a linked copy is not sufficient proof on its own when the tool can be pointed at its own repository.

Prevents: a worker doing its work in your primary checkout, which turns a routine task into a recovery operation.

P12 Cleanup refuses when it cannot prove the work landed

Removing an isolated copy requires positive proof that its work is reachable from a remote branch, or its pull request merged with a head containing the work, or its content is already present in an up-to-date default branch. Anything inconclusive refuses.

A refusal is a result that means stop and investigate. It is not an obstacle to work around with a force flag.

Prevents: discarding a worker's committed but unlanded work because a lookup failed.

P13 You get outcomes, not mechanics

Everything Assistant says to you names the project outcome, the consequence, and the next decision. Internal terms do not appear: no task identifiers, no isolated-copy paths, no watcher or wake vocabulary, no stage names, no state labels, no compressed safety jargon. Worker reports and tool output are evidence to read, never text to relay.

Detailed evidence documents may keep exact identifiers. The message that points you at one still translates.

Prevents: a tool that is technically correct and practically unusable, because using it requires holding its implementation in your head.

P14 Every fact has exactly one owner

A contract lives in one place. Everything else points at it. This applies to documentation, to configuration, and to code: when two mechanisms would judge the same question, reconcile them into one rather than stacking them.

Prevents: duplicated rules drifting apart, and the specific version of that where two independent reviewers both feel responsible and neither is.

Section 5

The delivery gate

The gate is one deliberate place where validation happens before a branch is shared. It is not an abstraction over git; it is a local bare repository that git can push to normally.

Setup

Initializing a repository does five things, and repeating it repairs rather than fails:

  1. Create a local bare repository, identified by a stable hash of the working path.
  2. Install an admission check that runs before any reference changes, and a notification that runs after.
  3. Add a remote named assistant to your working copy pointing at it. Your origin is untouched.
  4. Install the agent-facing instructions so a coding agent can drive the same gate.
  5. Make sure the background service is running.

If the working copy moves, initialization reattaches the existing gate and keeps the run history. If the working copy was copied while the original still exists, the copy gets its own gate.

The nine stages

The order is fixed. What each stage runs is yours to configure.

The review fix round has a condition attached

Letting review fix its own findings automatically is the one place where P4 and P5 are most likely to be violated by accident, because the fixer has just been told exactly what to change and it is tempting to let it confirm its own work. Two rules make the round safe, and both are load-bearing rather than optional.

  • The round covers fix findings only. An ask finding never enters it, so the round can never resolve a question that was yours to answer.
  • The re-review after the round runs in a fresh session with no memory of the fix, and it treats the fix commit as author code. It receives the previous findings and the fix summary as claims to check, never as evidence that anything was resolved.

If either rule is dropped, this setting becomes the exact failure P4 describes: the reviewer certifying its own prescription.

Why review comes before test

If tests run first, their fix rounds modify the code, and review then reads code the fixer wrote rather than code you wrote. Reviewing first keeps the reviewer's subject the actual change. This ordering is load-bearing, which is why the order is not configurable.

Findings and their actions

A finding has a severity (error, warning, info) and an action. The action decides who resolves it, and it is the single most important field in the system.

fix

Objectively wrong and mechanically fixable. Eligible for the automatic fix loop.

Correctness, reliability, and security issues stay here even when the smallest correct fix restores a little previously deleted logic.

ask

Touches your intent or your judgment. Holds for a decision; never enters the automatic fix loop.

Questioning a deliberate product choice, arguing an intentional removal should be undone, or reporting that a stage could not gather enough evidence.

note

Informational. Needs no fix and blocks nothing.

A stage whose findings are all notes is approved as it stands.

Missing action means ask

If a finding arrives with no action, an empty action, or an action the system does not recognize, it becomes ask. This is not an error path to log and move past; it is the defined behavior, and it is what makes P3 hold when an agent's output is imperfect.

What a review report has to carry

A finding is a claim about code, and a claim is worth what a reader can check. So a review report carries the revision it read and the set of paths it actually read. This fixes a property of the report, not a field name or a wire shape.

  • A report whose revision is not the commit the stage was asked to review is refused rather than credited. A reading of some other commit is not a review of this change.
  • A finding whose location names a path outside the declared evidence set is refused, and it is reported as refused with the path it named. A reviewer asserting past what it read is visible rather than quietly trimmed.
  • A finding with no location and no explicit citation normalizes to note. Nothing supports it, so it may inform you and may not stop a run.
  • That last rule does not reach P3. A finding whose action is missing, empty, or unrecognized becomes ask and stays ask; normalizing to note applies only where the reviewer stated an action the system recognized.

The evidence set has to be able to fail

A reviewer satisfies the rule above by declaring every changed file and nothing else, and then reading nothing but the diff. That declaration is derivable from the run without asking the reviewer, so on its own it proves nothing about what was read. A check that can pass without checking anything is worse than no check, so the discriminator belongs in the requirement rather than in a later reading of it.

  • The evidence set and the change's own set of touched paths are reported separately and compared. The discriminating part is the paths the reviewer read that the change did not touch, and that part is reported whether or not it is empty.
  • A finding asserting something about code the change does not touch, such as a caller, an interface, or a test that covers it, cites that code, and the finding is refused unless the evidence set names the cited path. Declaring the diff wholesale therefore buys nothing: it forfeits every finding that reaches past the diff, which is most of what an independent review is for.
  • An evidence set equal to the touched paths is a permitted outcome, not an error. Small changes need nothing else, and a guard that failed here would fail on correct work. What it may not be is invisible: it is a reported outcome, so a reviewer that never reads past the diff is a fact you can see across runs rather than a possibility you have to assume away.

Scope as a review lens

Every changed line should trace to the stated intent. That is a lens the review stage applies, and it ships in the default review guidance rather than as a stage of its own. P2 fixes the list at nine and this adds none.

  • A scope observation is a note by default. It informs you, blocks nothing, and never enters the automatic fix loop.
  • It rises above note only when it independently meets the bar for fix or ask. A line being unexplained is not that bar. A change nobody asked for that is also wrong is reported for being wrong.
  • The lens is measured against the recorded intent and inherits that intent's source. Against supplied intent it compares a change to acceptance criteria; against inferred intent it compares a change to a low-confidence hint, which is the second reason its default is note.
  • Being guidance, it is strengthened the way review is strengthened anywhere, through path-scoped review rules. No key in the configuration schema turns it off, and turning it off would not skip a stage, because it is not one.

Recurring findings become a proposal, never a rule

A class of finding that keeps recurring across runs of the same repository is usually a missing review rule rather than a run of accidents. Assistant may say so. It may not act on it.

  • A recurring class may be raised as a note proposing an addition to that repository's path-scoped review rules, for a person to accept or discard.
  • The proposal names the class and the runs it recurred in, so the reader checks the pattern instead of taking a count on faith.
  • It is never applied and never inferred into effect. The review rules in force for a run are exactly the resolved configuration, and path-scoped rules are read only from the trusted copy, so accepting a proposal means a person putting the rule on the default branch.
  • Being a note, it holds nothing and enters no fix round.

The fix loop and its three bounds

When a stage returns fixable findings and its limit allows, the fixer applies them and the stage re-runs to verify. This is the one cycle in the whole design, and unbounded cycles are the most common defect in systems of this shape, so it carries three independent bounds.

The loop has three outcomes and not two, and anything that redraws the diagram below has to keep room for all three. A finding that needs your decision holds. A stage whose fix round limit is zero holds as well, because it has no fixer to send the finding to. A limit or a budget that is spent, or a round that changed nothing, parks. A hold waits for you; a park stops the run.

What you do at a hold

A hold offers four actions, and they are the same whether you act through the terminal interface or an agent acts through the machine interface.

ActionEffect
ApproveAccept the findings as they stand and advance.
FixRun one fix round over the findings you selected, with any notes you attached and any findings you wrote yourself. The stage re-runs and holds again so you see the result.
SkipMark this stage skipped for this run only.
CancelEnd the run. Work stays recoverable.

What the fixer receives for a round is the selection you made, your notes, your own findings, and a sanitized history of earlier rounds including which findings you deliberately left unselected. A later review uses that history to avoid re-reporting something you already decided about, unless the code now presents a materially different issue.

What passing the gate means

Exactly this, and nothing more:

  • The branch was rebased onto freshly fetched upstream and branch targets.
  • Review, targeted tests with evidence, documentation, and lint all ran before anything was pushed.
  • You stayed in control of every judgment call, or you explicitly consented to a bounded amount of unattended resolution.
  • The branch update was checked against the live target and refused rather than guessed at.
  • The pull request records what was checked, what was fixed, and how many attempts it took.

The gate does not define compliance. It publishes facts precise enough for any external system to reach its own verdict.

What the gate does not establish

One limit is worth writing down now rather than meeting it later. The gate validates a diff. It does not establish where the intent behind that diff came from.

A worker steered by content it read while working produces an intent the intent stage records faithfully, and a diff that implements that intent consistently. Review, tests, and lint still read the change on its merits, so this is not a bypass of them: a change that is wrong is still caught for being wrong. The scope lens is the part that gives no warning at all, because every changed line does trace to the stated intent. The lens measures a change against the intent; it never asks where the intent came from.

Nothing in this document closes that. P7 bounds what a pushed branch may execute, may configure, and may claim about a validating agent's authority, which is a different question from what a worker was persuaded you wanted. A change that passes the gate has been validated on its merits. Passing is not evidence that the intent behind it was yours.

Section 6

The orchestrator

The coordinator turns one request from you into supervised work, and turns many workers' output back into a small number of decisions for you.

Delivery task

  • Deliverable is a change to a project.
  • Works on its own branch in its own isolated copy.
  • Reaches a shared branch only through the gate.
  • Its isolated copy is protected; cleanup refuses on unlanded work.

Investigation task

  • Deliverable is a self-contained report with evidence.
  • Creates no branch, pushes nothing, opens no pull request.
  • Its isolated copy is declared scratch and is discardable.
  • Can be promoted to a delivery task in place, keeping its context.

A report is evidence, not authorization

A diagnosis, a recommendation, or an implementation-ready finding does not authorize changing code. Implementation is a separate request. Promotion is the explicit mechanism: it flips the task's contract in place, in the same terminal with the same loaded context, so the protections that apply to delivery work start applying.

Events and current state

This is P8 made concrete, and it is the highest-value single change in the whole design. Two records exist per task, and they answer different questions.

RecordShapeAnswers
Event logAppend-onlyWhat has happened to this task, in order. Each append is a wake. Never read its tail to decide what is true now.
State recordAuthoritative, one ownerWhat is true now. Resolved deterministically, with the source of the answer attached.

The state resolver answers in a fixed precedence:

  1. A validation run attributed to this task's own branch, whether active or finished. This outranks everything, because a worker handed off to the gate stops writing to its own log.
  2. A live process signal from the task's terminal.
  3. The event log, and only when its most recent event maps to a recognized state.
  4. Otherwise, unknown. A dead terminal with no attributed run reports unknown rather than trusting a stale event.

An event that closes a decision is decision-only: it never becomes current state, and its text never leaks into the state detail. If the log's last event says a decision is open but the validation run has moved past it, the resolver reports that event as superseded.

Supervision

A watcher process blocks on the fleet and classifies every wake without invoking a model. It absorbs a wake only on positive evidence of progress. This is what makes running many workers affordable, and it is also where the design is easiest to get subtly wrong.

Absence of evidence surfaces

A wake is absorbed only when something positively proves work is proceeding. A worker that finished, crashed, or silently stopped produces no such proof, so it surfaces. Never absorb on elapsed time alone.

The queue is durable and written first

An actionable wake is recorded before any detector state advances, so a missed process exit is recoverable by draining. Every turn that handles a wake drains the queue before doing anything else.

A declared wait is not a stall

A worker waiting on something external that will clear on its own says so. That silences the stall detector but arms a slower recheck, so a forgotten wait cannot stay invisible indefinitely.

A terminal-ish wait surfaces once

A worker that finished and is waiting on a merge, or that stopped on a blocker, surfaces once, then is absorbed even as its idle screen redraws, then surfaces again when something actually changes. Otherwise it storms every poll.

Keeping supervision alive

P10 is defended four independent ways, because a single mechanism has already failed in practice and the cost of that failure is hours of silence.

LayerDirectionWhat it does
The live cycleActiveThe coordinator holds exactly one supervision wait whenever work is in flight, resumed as the last action of every turn.
Arm verificationActiveStarting a watcher confirms it is genuinely alive with a fresh liveness beacon and reports an honest started, attached, or failed. An unexplained exit is a typed failure, not silence.
Pull guardPassiveOrdinary commands warn when work is in flight and the watcher has stopped, or when queued wakes are waiting to be drained.
Stop guardPushWhen the coordinator tries to end a turn while work is in flight and no matching live watcher holds this home's lock, it is blocked or forced into one bounded follow-up turn.

Never kill watchers broadly

A pattern-matched process kill reaches watchers belonging to other homes on the same machine. Repair goes through the home-scoped owner path, which signals only the watcher recorded in this home's lock. Command shapes that violate this should be refused before they run, not cleaned up after.

What reaches you, and how it is worded

Reaches you immediately

  • Work ready for your review, with the full pull request URL.
  • Finished investigation findings, relayed as findings rather than as a completion notice.
  • A finding that needs your decision.
  • A real blocker after the recovery path is exhausted.
  • Anything destructive, irreversible, or security-sensitive.
  • A credential or sign-in you need to provide.

Never reaches you

  • Automatic fixes and retries that succeeded.
  • Routine progress and elapsed waiting time.
  • Internal supervision mechanics of any kind.
  • Raw worker reports, event lines, or tool output.
  • An unchanged fleet reported as if it were progress.

Every escalation stands alone and leads with evidence, then the consequence, then the options, then a recommendation. The same evidence-first shape applies when Assistant disagrees with you: it states the evidence rather than deferring.

The selected path owns its own rigor

When the gate is selected, the gate alone owns review, fixes, tests, documentation, and delivery. When it is not, take the faster path without inventing an extra reviewer. Never stack a second manual review on top of a gated run, and never hold gated work outside the pipeline for a separate clean verdict. If a fast path feels too risky, the decision to escalate is whether to use the gate, not whether to add a review nobody specified.

The autonomy flag

Off, by default

You own every ask finding, every merge, and every local fast-forward approval.

On, by your explicit instruction

Assistant resolves routine gates itself and merges work that is green or already approved. It still escalates anything destructive, irreversible, or security-sensitive, and it never merges a failing pull request. Every autonomous merge produces a one-line outcome with the full URL.

Automating judgment expands only when you say so, never by a default changing underneath you. Being away from the machine never expands this authority: it changes how you are reached, not what may be decided without you.

Section 7

Execution model

Both halves of this product are graphs already. The pipeline is a linear sequence with a fix cycle and human decision points. The fleet is a set of independent supervised runs. Neither is written as a graph today, which is why resuming, displaying, and reasoning about them is harder than it should be.

The decision

Rejected

Keep it hardcoded

A fixed sequence plus a state file, as today.

Cost: resume logic is bespoke per stage, progress display is derived by parsing logs, and every new pause point is a new special case. Both source projects show the accumulated cost of this.

Rejected

Adopt a workflow engine

Build on an existing agent-graph or durable-execution framework.

Cost: a dependency, a domain-specific language, and a migration, to gain features this product needs a fraction of. A local single-user tool should not require a cluster, and none of the surveyed engines fits a local process model without pulling in most of their world.

Recommended

Reify the graph you already have

Make the existing topology an explicit, small, in-house structure.

Buys: resume from a checkpoint instead of from stage boundaries, a live progress view that reads structure rather than logs, static checks over the topology, and one place where pause and resume are defined. Roughly one module, not a platform.

This is a survey result, not a preference

The graph frameworks in this space are converging on a shape worth copying and away from a shape worth avoiding. Two of the leading agent libraries deleted their own built-in persistence during 2026 and now plug into external durability substrates. One major vendor shipped a visual workflow graph, deprecated it within eight months, and documented that workflows "requiring strong determinism at their core may not migrate faithfully." Both the gate and the fleet are squarely in that category, so the lesson is to own the determinism and keep the machinery small.

Two different shapes for two different problems

The gate is a bounded cyclic step graph

Nodes are stages, one edge is a back edge for the fix loop, and some nodes halt before running to wait for you. State is a typed record with declared merge rules. Determinism matters more than throughput.

The fleet is supervised independent runs

Each task owns its own graph instance and advances on its own clock. There is no barrier between phases, because worker latency varies by orders of magnitude and a barrier would idle every fast task behind the slowest one.

The minimum viable abstraction

Five concepts. Everything else is built from them.

ConceptDefinition
Node A named unit of work that reads declared state keys and writes declared state keys. Declaring what it reads and writes is what makes replay and forking possible, so it is required, not optional.
Edge A transition, either unconditional or guarded by a predicate over state. Back edges are permitted and must be bounded. An edge is data, not a callback.
State A typed record. Every key that more than one node can write declares a merge rule. A key with no declared rule may be written by exactly one node.
Halt point A marker on a node meaning "stop before running this and wait for a decision." The node does not start. Its inputs are already in state, so nothing needs to be re-executed on resume.
Checkpoint State plus position plus any open decision, written after every node, plus once when an executing segment claims the run. That claim write is what lets a second caller be refused before it starts a node rather than after, so a node body is not run again by a caller that has already lost the run. Restoring one re-emits the open decision. One call can restore and answer together.

Halt before, not interrupt inside

There are two ways to model waiting for a person, and the difference is not cosmetic.

Interrupt inside the node

The node starts, runs partway, and suspends. Resuming re-runs the node from the top with the answer injected, so everything before the suspension point must be idempotent. That requirement is invisible in the code and easy to violate later.

Halt before the node runs

The graph stops at the boundary. The node never starts, so there is nothing to make idempotent and nothing to replay. The decision is collected outside the graph and supplied as input on the next call. This is also exactly how both source systems already hold work.

Use halt-before. It is strictly simpler, and it makes P6 easier to hold because a paused run has performed no partial side effects that a resume might repeat.

Rules the topology must enforce

1

No two nodes write the same key without a declared merge rule.

Checked when the graph is built, not at run time. One popular framework removed its thread-safety wrapper and now has a reproducible bug where the same definition produces different business results depending purely on scheduling. Declared merge rules are the fix.

2

Every back edge carries a bound at construction time.

A graph with an unbounded cycle fails to build. Most surveyed frameworks ship no default cycle guard at all, and one defaults to running until something escalates, which is to say forever.

3

A cycle that passes through a join must include that join's fork.

Otherwise the join can be re-entered with a partial set of inputs and produce a result that looks complete. Only relevant once fan-out exists, which is why it belongs to a later phase, but the rule should be in the checker from the start.

4

Node implementations are constructed per run, not shared.

A single background process runs concurrent validation runs. Sharing node instances across them is a defect class that only appears under concurrency, which is the worst time to find it.

Topology and durability are separate layers

Keep the interface between them to four operations. The default implementation writes to the local embedded database that already holds run state, because a local development tool must not require a server. Keeping the boundary narrow means the substrate can change later without the topology layer noticing.

Two of those four operations are a run's whole history and a fork from a point in it, so the record behind them is a history and not a row rewritten in place. That record is section 8's checkpoint history, and a run's position is written to and read from there and nowhere else. No other record may hold a copy of where a run stands.

The checkpoint store is inside the trust boundary

Checkpoints are resumed with your credentials, so a tampered checkpoint is a code-execution path. Use a data-only serialization format, validate on read, and never load a checkpoint from a source outside this home. This is the same rule P7 applies to configuration, extended to run state.

Section 8

Architecture

This section is language-agnostic on purpose. It fixes the module boundaries, the data model, and the process model, and leaves the implementation language, libraries, and testing tools to you.

What the coordinator is

The coordinator is two things with a hard line between them. An agent handles conversation, intake, and judgment. A program owns every state change, every refusal, and every guard. The agent decides what should happen; the program decides what is allowed to happen, and it is the only thing that can make it happen. 

flowchart TB
  you["You"] <--> ag["Coordinator agent
conversation, intake, judgment"]
  ag -->|"typed commands only"| pr["Coordinator program
state, guards, refusals"]
  pr -->|"structured results and refusals"| ag
  pr --> st[("Authoritative state")]
  pr --> gate["The gate"]
  pr --> fleet["Workers and sessions"]
  ag -.->|"cannot reach directly"| st
  ag -.->|"cannot reach directly"| gate

The agent owns

  • Understanding what you asked for, and which project you meant.
  • Choosing a task shape, writing the instructions, and deciding when work overlaps.
  • Reading a report or a finding and deciding whether it needs you.
  • Translating internal state into the outcome you hear, per P13.
  • Every judgment the autonomy flag permits it to make.

The program owns

  • Every write to state, and the resolver that reads it back.
  • Every guard: isolation, custody, data loss, cleanup proofs, the trust boundary.
  • The graph, its checkpoints, and every hold.
  • Supervision, the wake queue, and the stop guard.
  • Every refusal, and the reason attached to it.

The split only holds if the agent has no second path

A hybrid degrades into a pile of instructions the moment the agent can reach around the program: run a raw git command, edit a state file, kill a process. Then every guard becomes a rule the model is asked to remember, and P6, P11, and P12 all become advisory. Three rules keep the line real, and they are worth enforcing mechanically rather than describing.

  • State files and gate repositories are written by the program only. The agent has no direct write path to either.
  • A refusal is a typed result the agent must report, not an error it may retry a different way. There is no force flag reachable from the agent side.
  • Command shapes that would bypass the program are refused before they run, not detected afterwards.

The practical test for which side a behavior belongs to: if getting it wrong loses work, breaks isolation, or weakens what a pass means, it belongs to the program. If getting it wrong produces a worse decision that you can see and correct, it belongs to the agent.

An adapter declares what it supports, and undeclared means unavailable

Agent adapters differ in what they can do, and that difference has to be a declaration the program reads before it commits to a path, not something a stage discovers halfway through one. Each adapter declares its capabilities. A path the resolved adapter has not declared is refused before that adapter is launched, naming the capability that is missing, and is never replaced by a weaker path that would still be reported as a pass. Section 10 already specifies this shape for instruction suppression; this generalizes it to the rest of the interface.

The case that decides whether this is worth having is P4. A review may never resume the session that prescribed the fix it is checking, and a fixer session is the only memory that crosses a round. So an adapter that has not declared resumable sessions gets no substitute for one: nothing shared, replayed, or reconstructed may carry a fixer's memory into the review that checks it. Either the run has a declared session or it has no memory across rounds. Running both roles in one session is not a degraded mode that an undeclared capability may fall back to.

Data model

The important part is not the field list; it is which records are authoritative and which are history. One record is both, and it is called out below.

RecordKindNotes
repositoryAuthoritativeWorking path, upstream and optional fork, default branch. URLs are stored with credentials removed; the credentialed URL is recovered from the gate at run time.
runAuthoritativeBranch, submitted head, base, current head, status, the commit a completed review approved, the push binding, pull request state, intent and its source, and the exact build that produced this run.
stage resultAuthoritativePer stage: status, findings, duration, log path, last activity, and the effective fix limit.
roundHistoryOne row per stage execution. Findings, which findings were selected and by whom, the exact payload sent to the fixer, and the one-line summary. This is what the pull request narrative is generated from.
checkpoint historyAuthoritative, appendedOne entry per position a run has stood in: state, the node it has not yet run, the status it stood in, the decision it is halted on when it is halted, the bound accounting, and, on an entry a fork produced, the entry it was copied from. taskAuthoritativeShape, project, mode, isolated copy path, session reference, linked run, linked pull request.

A run's position has exactly one record, and it is appended

The checkpoint history is the one record here that is appended and never revised and still answers a present-tense question. That is not the failure P8 names. P8 forbids inferring what is true now from a log of things that happened, and there is nothing here to infer from: every entry is a whole position, complete on its own. Which entry is the latest is the sequence the store assigned it, decided under the same serialization that decided the write's anchor, rather than whichever row was appended most recently.

There is one checkpoint record and there may not be a second: no row per run rewritten in place holding the same state, position, and open decision alongside the history. Section 7's durability layer has to answer a run's whole history and a fork from a point in it, which such a row cannot, so the history replaces it rather than sitting beside it. Two records for one fact is the P14 failure whichever of the two a reader ends up believing, and the rewritten summary is the one that would go stale unseen.

Two schema rules worth fixing now

Schema changes are additive, and a column added later reads back as unknown for old rows, never as a fabricated zero. A surprising result must always be traceable to the exact build and configuration that produced it, so record both on every run.

Every hold resolution records who resolved it

A hold is closed only by an explicit resolution, and that resolution carries who made it, drawn from a closed set of values. The set is closed, so there is no free-text alternative that could grow into an unaudited one. The value meaning a person decided cannot be produced by any path an agent reaches, on any surface. An agent driving the machine interface resolves holds with the same options and the same authority as you, per section 9; what it cannot do is produce a record saying a person decided.

This records, it does not gate. Nothing reads the value to decide whether a resolution is allowed, and no resolution that standing authority permits today may become refused because of what it would say. It exists so a run's history answers who made each call directly, rather than by inferring it from what the autonomy flag happened to be at the time.

On-disk layout

Everything lives under one root, relocatable by environment variable. One root is one home.

<home>/
  config.yaml            global configuration
  state.db               the embedded database
  lock                   exclusive lock held for the service lifetime
  socket                 local endpoint for the command line and agents
  repos/<id>.git         bare gate repositories, id from a hash of the working path
  worktrees/<repo>/<run> disposable isolated copies, removed when a run ends
  evidence/<run>         test evidence, deliberately outside the isolated copy
  tasks/<id>/            per-task records: instructions, report, state, events
  queue/                 the durable wake queue
  logs/<run>/<stage>.log per-stage logs, the authoritative full output
  logs/service.log       bounded lifecycle log with rotation
  • Evidence is never inside the isolated copy. Test artifacts must not become part of the change being validated.
  • The full log is the authority. What appears in findings, streams, and prompts is a bounded projection with an explicit marker naming what was omitted and how to read the rest.
  • Log rotation truncates in place. A service or child process holding an open descriptor keeps writing to the bounded file rather than to an orphaned inode.
  • Records precede directories. Insert the run row before creating its directory, so a directory with no row is always safe to remove.

Two boundaries that are easy to get wrong

Process lifetime

Agent processes are scoped to the invocation that started them. On completion, failure, or cancellation, terminate the whole process tree, escalating from a polite signal to a forceful one after a grace period. A descendant that detaches from its process group escapes that, so keep an identity-based sweep that matches processes by the isolated copy their working directory resolves under, never by command line. It must never touch a copy whose run is still active.

Event delivery

Streams are bounded, so overflow is a design decision rather than an accident. Classify events as activity, state, or control. Bounded, never blocking the executor, and never evicting state is a trilemma, so the property that holds is that state is never silently dropped: activity is discarded first, a state event may be evicted only when that eviction is collapsed into the sticky gap marker, and control is never discarded. Publishing never blocks the executor. Anything dropped collapses into one sticky gap marker that is delivered ahead of queued payload, so a consumer learns it is missing something before it acts on what follows. Every state event carries a monotonic revision, and every subscription opens in the gap state so attaching always reconciles first.

Terminal interface

One screen that answers four questions in order of urgency. It adapts from a two-column layout to a stacked one on narrow terminals.

Where am I?

All nine stages with status icons, durations on completed stages, and a fixed count on stages that fixed something.

Why did it stop?

The findings list with a risk header, selection checkboxes, severity, location, and any note you attached.

What changed?

The diff for the fix round, loaded on demand. If it cannot load, approval is disabled rather than offered against unknown content.

What is happening now?

A live log tail, and while checks are running, the pull request state and a clear signal once checks are green.

Design constraints: use only the terminal's own palette so it follows the user's theme; keep a fixed-width gutter so content never shifts as the selection moves; and reflect run state honestly. Working, waiting on a person, and dead must be visually distinct, because a stall that looks alive is worse than an error.

Machine interface

An agent drives the same gate through a structured command family. The contract has five parts.

ElementContract
Blocking callsStarting or responding blocks until the next decision point or a terminal outcome. A long call is working, not stalled, and a run never advances past a decision on its own. The bare start attaches, so a run already being advanced is reported where it stands rather than advanced twice, and that one call returns executing instead.
Structured outputMachine-readable on standard output, progress on standard error. Control characters are escaped visibly rather than emitted raw.
Stable exit codesSuccess and normal decision points; operational failure; incorrect usage. Three meanings, never overloaded.
OutcomesSix, in two groups. Four say a run is finished with. checks-passed means validated and green but not merged, and it means stop driving and ask the person. passed means merged or closed. Failure and cancellation are terminal and require a next action, never silence. Two say it is not. decision is the decision point a blocking call returns at, and executing is a run still advancing, which only an answer that reported the run without advancing it can carry. Every outcome carries a next action, terminal or not.
Relay verbatimA finding that needs a decision is relayed with its full text, unsummarized and unjudged, unless standing consent to resolve unattended was given.

Why the terminal four are the whole answer to how a run ended

The four terminal outcomes answer one question: how did this run end. That is the question a blocking call asks, since starting or responding does not return while the run is still moving, and every way a run can be finished with is one of the four. They were not an incomplete list of run states; they were the complete answer to that question.

A read asks a different one: where does this run stand right now. Reporting status, and reporting one run by identifier, answer without advancing anything, and a run part way through a stage has no terminal answer to give. Reaching for one of the four there says something false about it. executing is the answer that was missing, and it relaxes nothing above it: a call that did advance the run still returns at a decision point or with a terminal outcome.

Attaching straddles the two. It blocks while it advances the run, but a run already being advanced is reported rather than advanced a second time, and that report can be executing: attaching asks where a run stands, and that it is moving is an answer to that. A caller never answers executing, because there is nothing to answer. Its next action is to attach, which carries the run on and blocks until its next decision - unless the service is already advancing it, where the answer comes at once and the caller pauses before asking again.

Rich intent is required, not optional

A driving agent supplies your goal in your terms, plus the decisions, tradeoffs, and constraints behind it, and the approaches you ruled out. A one-line summary of the diff makes the reviewer flag choices you already made deliberately, which is the fastest way to make the gate feel like an obstacle.

An agent already running inside a validation stage is contained: it may inspect, fix, and return its own stage, and nothing else. Attempts to start, stop, respond to, or push around a pipeline return a specific containment error. An environment marker is diagnostic evidence only, never authorization; authority comes from authenticated process ancestry.

Read from the pushed branch

Fields that cannot execute anything or weaken a check. A contributor may set these freely.

Commands and agent selection. These run shell and choose which process starts with your credentials. The opt-out exists for a single-developer repository and is itself readable only from the trusted copy, so a branch cannot enable it for itself.

Always trusted-only

Anything that shapes what review or documentation demands, or that declares a check unnecessary. A contributor must never be able to suppress a maintainer's review rule from their own branch.

Global-only

Fields a repository may not set at all, in either copy. These are operator preferences about how this machine behaves rather than facts about a repository, so a repository should not set them even where doing so could not weaken a check. The test is authority, not harm.

If the trusted commit cannot be fetched, or its configuration file cannot be read and parsed, the run stops before launching any agent. It does not guess at defaults. A readable tree with no configuration file is valid and uses defaults; that is a different case and must be distinguished.

  • Reserved agent flags that would defeat managed behavior are rejected at load rather than silently ignored.

Section 11

Failure and recovery

Failure is a first-class outcome: loud, attributed, explained, and followed by a next action. A restart should be a non-event.

Service restart

On startup, after taking the exclusive lock and before serving anything:

  1. Complete runs whose recorded pull request is already merged or closed.
  2. Resume only fully recorded holds whose isolated copy and stage history both validate. An ambiguous or partially recorded active run fails closed rather than resuming on a guess.
  3. Before resuming a hold that waits on external checks, re-read the pull request. Merged or closed completes the stale hold; open, unknown, or unreachable stays held.
  4. Mark every other stale active run failed, with the reason recorded.
  5. Reap orphaned agent processes, remove isolated copies no run owns, and never touch one whose run is still active.
  6. Clear any waiting-on-a-person marker so a recovered failed run is not displayed as still waiting.

Fleet reconciliation

Fleet state lives on disk and in the live session provider, never in conversation memory. At session start the coordinator does a cheap presence check per task, then reconciles only the tasks recorded in this home. It never sweeps a shared namespace or claims another home's work.

SituationResponse
Terminal gone, work not landedPreserve the isolated copy. Prove no live process owns it, then relaunch in that same copy with the same instructions plus a note about what already happened. Never a fresh generic launch while the copy is unaccounted for.
Terminal alive, screen unchangedOnly a stall if nothing positively proves progress. A worker thinking for a long time is not stuck.
Repeated stall on the same unchanged screenEscalates. After enough repetitions it demands a deeper inspection rather than another surface look.
Ambiguous livenessLeave it alone. Relaunching on an ambiguous reading risks two supervisors for one task, which is worse than one late check.
Queued wakes present at startDrain before doing anything else, including before reading further.

Custody of your branch

Because the pipeline commits fixes in a copy, your local branch can fall behind or diverge from what the pipeline holds. One service owns every mutation of your branch, and it classifies before it acts.

ClassificationMeaning and next action
Pipeline holds itA run is active. Wait for it.
RecoverableA terminated run moved the head. Recovery brings that work back to you.
Yours alreadyTermination positively verified the head never moved. Nothing to do, and recovery is a no-op.
BehindFast-forward a clean checked-out branch to a freshly verified pushed commit.
Diverged but equivalentContents match. Anchor the current head under a recovery reference first, then move.
Genuinely divergedBlocked. Nothing changes and you are told why.

Never

Stash, merge, rebase, force, switch branches, delete a branch, or touch a remote. Reading status never fetches and never mutates.

Adopting a diverged head requires proof

An executable three-way merge whose result matches the preserved tree, anchored on the merge base. Comparing patch identity is not sufficient: it discards hunk locations and whitespace, so it cannot tell a genuine replay from a similar edit somewhere else. Anything undecidable escalates.

Recovering an investigation

An investigation task's isolated copy is scratch, but its report is not. The report survives cleanup, and any decision the investigation surfaced must be registered as a durable hold before the task can be treated as complete. Cleanup verifies that registration and refuses without it. A hold is not closed because the investigation finished, the report was filed, or the task was cleaned up. It is closed when you answer it.

Section 12

The MVP cut

The source projects have a combined surface area of roughly a hundred commands, five session providers, seven agent adapters, and four delivery paths. Most of that breadth is real, earned response to real problems, and almost none of it is needed to find out whether the core idea works for you.

Phase 1

The irreducible core

Everything here is load-bearing. Removing any one of them removes a promise.

  • The gate: named remote, bare repository, admission and notification, background service.
  • All nine stages. Cutting one breaks P2.
  • Findings with three actions and the fail-closed default.
  • The fix loop with all three bounds.
  • Holds, the four actions, and durable resume.
  • The graph layer with halt points and checkpoints.
  • The data-loss rules in full. This is not phaseable.
  • The configuration trust boundary in full. Also not phaseable.
  • Claude Code as the only agent adapter, behind the full adapter interface. It has a native output schema and resumable sessions, so the structured-output and session-reuse paths are exercised properly rather than stubbed.
  • One forge adapter.
  • Fleet: both task shapes, dispatch, isolation assertion, the authoritative state record, cleanup proofs, and promotion from investigation to delivery.
  • Decision holds raised by an investigation, and the cleanup check that refuses without them.
  • The watcher, the durable queue, and the stop guard.
  • The terminal interface and the machine interface.
Phase 2 and later

Deferred, with reasons

  • Agent adapters beyond Claude Code. Each one is a week of quirks, and agents without a native output schema need a whole parsing path. Build the interface now, the adapters when you need them.
  • Extra forge adapters. Same reasoning. Do not promise breadth ahead of demand.
  • Extra session providers. One reference provider proves the abstraction. Four more prove nothing new.
  • Delegate coordinators. The most complex feature in either source project. It only earns its cost at a fleet size you have not reached.
  • Direct and local delivery modes. The gate is the thesis. Adding modes that bypass it before it is proven undermines the experiment.
  • Transcript-based intent inference. Supply intent explicitly first. Inference is a convenience over a mechanism that must already work.
  • Away mode. Requires the supervision loop to be trustworthy first.
  • Evidence publishing to a branch. Store evidence locally and link it. Publishing is an optimization.
  • Review evaluation corpus. A quality tool for when review quality is your bottleneck.
  • Fan-out and fan-in in the graph. Nothing in phase one needs parallel nodes. Keep the checker rule; skip the feature.
Never

Permanent non-goals

  • Configurable stage order. It is the only thing making a pass comparable across repositories.
  • Standing configuration that skips a stage. Per-run skips by a person, yes. A rule that skips on your behalf, never.
  • Adding stages. A repository strengthens a stage; it does not add one.
  • Risk-based automatic skipping. A classifier's guess must never weaken what a pass means.
  • A hosted service. Your credentials, your machine, your initiative.
  • Owning merge policy. That belongs to your forge.
  • Being your CI. The gate is the inner check; CI stays the shared outer one.
  • Silent degradation. A gate that cannot run completely refuses and explains. It never quietly becomes a weaker check.

The one thing to build first

Before the graph layer, before the fleet, build the authoritative state record and its resolver. It needs no new infrastructure, it is the smallest change in this document, and it removes an entire class of wrong behavior: acting on a stale event because the tail of a log was mistaken for the truth. Everything else in the orchestrator reads from it.

Section 13

Verification

Each principle implies a test. Write these as the principles are implemented, not afterwards. Several of them are the only reason the corresponding rule stays true a year later.

RuleThe test
P1After initialization, an ordinary push to origin behaves exactly as before: same target, same refs, no run started.
P2No configuration path can reorder, remove, or add a stage. A per-run skip works; a configuration file attempting a standing skip is rejected at parse time.
P3Feed the parser a finding with a missing action, an empty action, and an unrecognized action. All three become ask. None is eligible for automatic fixing.
P4Assert that every review invocation is session-free and that only fixer invocations carry a session. This is a structural assertion over invocation records, not a behavioral one.
P5A run whose only changes came from a fix round still produces a full review of those changes, with the same finding schema.
P6A remote that advanced out of band with commits the run did not incorporate causes the push to refuse, not to force.
The lease anchor equals the head the run last observed, never a tip read immediately before pushing. Assert on the anchor value, since the wrong version always passes behaviorally.
Kill the service mid-run at each stage boundary. Every time, the work is recoverable and the classification is correct.
P7A branch that sets a command, an agent, or a review rule in its own configuration has no effect on what runs. The trusted copy governs.
An unreadable or unparseable trusted configuration aborts before any agent starts. A readable tree with no configuration file proceeds with defaults. These two cases are distinguished.
P8Given an event log whose last line says a decision is open, and a validation run that has moved past it, the resolver reports the run's state and marks the event superseded. Assert the resolver never reads only the tail.
P9A matrix over the wake classifier: for every combination of wake kind and evidence, assert absorb or surface. Include the case where evidence is absent and assert it surfaces.
P10With work in flight and the watcher killed, the coordinator cannot end a turn silently. Also assert that a stale liveness beacon blocks even when the process is alive, and that a fresh beacon with a missing lock also blocks.
P11Launching with a resolved path equal to the primary checkout refuses. Launching into a path that is not an isolated copy refuses.
P12Cleanup with committed, unpushed work refuses. Cleanup after a squash merge and branch deletion succeeds through the content check. A provider lookup failure that leaves the question open refuses.
P13A static test over every user-facing string: assert the required wording is present and assert the internal vocabulary is absent. Both directions, or it drifts.
P14A static test asserting each contract appears in its owner and does not appear anywhere else. The negative half is the one that actually holds the line.
GraphA topology with an unbounded back edge fails to build. Two nodes writing one key with no declared merge rule fails to build. A checkpoint restore re-emits the open decision.

End-to-end

One journey test running the real binary against a deterministic stand-in agent, covering the whole path: push, every stage, a hold, a fix round, a re-review, push, pull request, checks. Run it on every supported platform. Process spawning behaves differently enough across platforms that only an end-to-end run finds those differences.

Then use the tool on itself. Every change to Assistant goes through Assistant's own gate. That is the first calibration loop, and it is how a field incident becomes a regression test before it becomes a memory.

Section 14

Decisions recorded

Five decisions were open when this document was first drafted. All five are answered, and the rest of the document already reflects them. They are kept here because two of them changed the shape of phase one and a later reader will want to know why.

#DecisionWhat changed as a result
1 Claude Code is the phase-one agent adapter. It has a native output schema and resumable sessions, so the structured-output path and the fixer-session path are both real in phase one rather than stubbed. Everything still sits behind the full adapter interface, so the second adapter is additive.
2 Both task shapes ship in phase one. Overrides the draft, which deferred investigation tasks. Section 12 now includes promotion and the decision holds an investigation raises. The cost is a second lifecycle from the start; the gain is that dispatch, isolation, supervision, and cleanup all get exercised on work that carries no delivery risk.
3 The graph layer lands in phase one. As drafted. Resume, progress display, and hold semantics are correct from the first version instead of being retrofitted onto a sequence that already made assumptions about them.
4 The coordinator is a hybrid: an agent for conversation and judgment, calling a program that owns every state change. The largest architectural consequence. Section 8 now opens with the split, the ownership lists, and the three rules that stop it degrading into instructions. The test for which side owns a behavior: if getting it wrong loses work or weakens a pass, it belongs to the program.
5 Review gets one automatic fix round, over fix findings only. Overrides the draft default of zero. Section 5 carries the two conditions that make the round safe: an ask finding never enters it, and the re-review runs in a fresh session treating the fix as author code. Without both, this setting reproduces the exact failure P4 exists to prevent.

What to settle next

Nothing here blocks starting. These are the questions the first working version will answer better than any amount of further discussion.

  • Where the hybrid line actually falls. Section 8 draws it at state changes. The first week of use will find behaviors that are awkward on the side they were assigned. Move them deliberately, and keep the rule that decides.
  • Whether one automatic review round is enough, or too much. Decision 5 is the setting most likely to need tuning once you see real findings. Watch how often the round produces a change the re-review then objects to; a high rate means the round is not paying for itself.
  • How much investigation work you actually dispatch. If promotion turns out to be the common path, the two shapes may be better modeled as one shape with a delivery flag.
  • The second agent adapter. Not which one, but when. The signal is the first time the single adapter's availability blocks a run you needed.
